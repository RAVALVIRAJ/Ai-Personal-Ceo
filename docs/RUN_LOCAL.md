# Run Local Development (Ai‑Personal‑Ceo) 🚀️  (first‑time setup & daily start/stop)    This guide assumes you have **Docker Desktop**, **Ollama** (running on the host), and the desired model already pulled.    ## Prerequisites  1. **Docker Desktop** installed and running.  2. **Ollama** installed on the host (not in a container). Start Ollama with `ollama serve`.  3. Pull the LLM model you want to use, e.g.:  ```powershell  ollama pull llama3.2:3b  # or any model that fits your 4 GB VRAM  ```  4. (Optional) If you want a fallback OpenAI‑compatible provider, set `OPENAI_API_KEY` in `.env.local`.  ## One‑time setup  1. Clone the repository (already done).  2. Create the local env file – the scripts do this automatically, but you can also run:  ```powershell  cp .env.local.example .env.local  ```  3. Verify the model is available in Ollama:  ```powershell  ollama list | Select-String -Pattern $env:OLLAMA_MODEL  ```  If the model is missing, run the `ollama pull` command above.  ## Daily start – Windows  You can start the whole stack with a **double‑click** on `scripts/start‑local.bat` (or run `scripts/start‑local.ps1` from PowerShell).  The script performs:  * Checks Docker is running (`docker info`).  * Checks Ollama API is reachable (`http://localhost:11434/api/tags`).  * Ensures the configured model exists; offers to pull it.  * Copies `.env.local.example` → `.env.local` **only if** the file does not exist.  * Runs Docker Compose in detached mode and builds any changed images:  ```powershell  docker compose --env-file .env.local up -d --build  ```  * Waits (up to ~30 s) for the three health endpoints to return **200**:  * `http://localhost:3000` (frontend)  * `http://localhost:8080/actuator/health` (backend)  * `http://localhost:8000/api/v1/health` (AI service)  * Finally opens the browser to the UI: `http://localhost:3000`.  ## Daily stop – Windows  ```powershell  scripts/stop‑local.ps1  ```  This simply runs `docker compose down` (keeps the Postgres volume).  ## Reset local data – Windows  ```powershell  scripts/reset‑local‑data.ps1  ```  Prompts for confirmation, then executes `docker compose down -v` which removes the database volume (all data is lost).  ## macOS / Linux equivalents  The repo ships `scripts/start‑local.sh`, `scripts/stop‑local.sh`, and `scripts/reset‑local‑data.sh` with the same logic as the PowerShell versions (using `bash`, `curl`, and `docker`).  Make them executable: ```bash  chmod +x scripts/*.sh  ```  Then run `./scripts/start‑local.sh` etc.  ## Developer mode (no Docker)  If you prefer to run services directly:  1. **AI service** – from the repo root:  ```bash  cd ai-service  uvicorn app.main:app --host 0.0.0.0 --port 8000  ```  2. **Backend** – from the repo root:  ```bash  ./mvnw spring-boot:run  ```  3. **Frontend** – from the repo root:  ```bash  cd frontend  npm run dev  ```  The frontend already proxies `/api` to `http://localhost:8080` (backend) and `/ai` to `http://localhost:8000` (AI service) via `vite.config.js`.  ## Model tips for a 4 GB VRAM GPU  * Default model in the example: **llama3.2:3b** (fits comfortably).  * Good alternatives: `qwen2.5:3b`, `gemma:2b`.  * Verify GPU usage with:  ```bash  ollama ps  ```  The `GPU` column should show your GTX 1650.  * Keep `OLLAMA_NUM_CTX` (context length) at the default **2048**; larger values increase VRAM usage.  ## Optional fallback LLM provider  If you have an OpenAI‑compatible key (e.g. Groq), you can set:  ```dotenv  LLM_PROVIDER=openai  LLM_FALLBACK_PROVIDER=ollama  OPENAI_API_KEY=sk‑your‑key  ```  The AI service will try Ollama first; on failure it will fall back to the OpenAI provider (internet required).  ## Backup & restore the database  ```bash  # Export  docker exec -t <postgres_container_name> pg_dump -U postgres -d ai_personal_ceo > backup.sql  # Restore  cat backup.sql | docker exec -i <postgres_container_name> psql -U postgres -d ai_personal_ceo  ```  Replace `<postgres_container_name>` with the name shown by `docker compose ps`.  ## Troubleshooting  * **Docker not running** – start Docker Desktop and re‑run the start script.  * **host.docker.internal unreachable** – ensure Docker Desktop uses the default networking (most Windows installs expose this hostname).  * **Ollama unreachable** – verify Ollama is running (`ollama serve`).  * **Port already in use** – stop any other process bound to 3000, 8080, or 8000, or change the ports in `.env.local`.  * **“Ollama offline” status** – the sidebar will display `-` for the model; double‑check the Ollama container is reachable from the AI service (`curl http://host.docker.internal:11434/api/tags`).  * **Email reminders not sending** – ensure `REMINDERS_ENABLED=true` and the SMTP settings are correct; if `SMTP_AUTH=false` set it accordingly.  ## Acceptance checklist  * [ ] `.env.local` created from the example.  * [ ] `docker compose --env-file .env.local up -d --build` runs without errors.  * [ ] Health endpoints return **200**.  * [ ] Frontend UI shows the sidebar with model label `-` when Ollama is down.  * [ ] `docs/PARITY_CHECKLIST.md` contains the table of LIVE vs LOCAL behaviours.  * [ ] All scripts (`*.ps1`, `*.bat`, `*.sh`) exist, are executable, and perform their described steps.  * [ ] Model tip section mentions a 4 GB‑compatible model.  * [ ] Backup / restore instructions are present.  * [ ] Troubleshooting section covers Docker, Ollama, port conflicts, and email reminders.  Once every item above is checked, the local development environment should be functionally equivalent to the LIVE deployment, differing only in configuration values.  Happy coding!
